# traviz

traviz is a Next.js 16 app for marking countries on a Mapbox globe as visited, want to go, or not interested. Each Clerk user's marks are stored in a Turso (libSQL) database. Read this file before you change anything. `CLAUDE.md` is a symlink to it.

## How the app works

- Routes: `/` (globe), `/list`, `/stats` (the account and reset controls are at `/stats#account`), `/sign-in` and `/sign-in/verify`. `src/proxy.ts` gates each request through `src/shared/route-gate.ts`, which reads the route's row in `ROUTES` in `paths.ts`. `signedIn` routes send signed-out users to `/sign-in`, `signedOut` routes send signed-in users to `/`, and `anyone` routes let both through. The match is exact, and a path with no row is treated as `signedIn`. Server Action POSTs skip the gate, so every action checks the user itself.
- Signed-in pages go under `src/app/(app)/`, whose layout renders the globe shell. The nav tabs come from `src/features/app-shell/navigation.ts`. A new route needs a function in `paths.ts`, a row in `ROUTES`, an entry in the routes list above, and a nav entry if it is a tab. `src/shared/paths.test.ts` fails when a `page` or `route` file under `src/app` has no row in `ROUTES`, and on any dynamic or parallel route, which exact matching cannot gate yet. Metadata files, such as a robots or sitemap file, are not checked. They reach the proxy unless the matcher excludes their extension, and with no row they get `signedIn`.
- Sign-in uses Clerk email links only. There are no passwords and no social providers. The form is custom code in `src/features/auth`. The root layout sets `prefetchUI={false}`, so Clerk's prebuilt UI bundle never loads.
- Marks are a `Marks` record from `src/features/marks/colors.ts`, keyed by country code. The pure reducer in `src/features/marks/marks-sync.ts` holds a base (empty, cache or server marks), the pending changes and the problems, and the screen shows the pending changes applied over the base. `src/features/marks/marks-owner.ts` runs the reducer and sends one change at a time, in tap order, tagged with the owner it was made for. A change with no reply after 8 s rolls back with an `unavailable` problem. When its reply comes later, the owner reads a fresh snapshot. `src/features/marks/marks-store.ts` wraps the owner in the zustand store `useCountriesStore`, which exposes `marks`, `ownerId`, `saving`, `problems` and the actions. A failed change undoes its colour and leaves a problem on its country, which `MarkStatus` shows. `src/features/marks/marks-cache.ts` keeps the last server marks and their owner in localStorage under `traviz-marks-v2`, so a repeat visit shows them at once. It removes the retired `traviz-marks` key.
- The store calls the actions in `src/features/marks/actions` as plain async functions: `applyMarkChange(expectedOwnerId, change)` for set, clear and reset, and `readMarks(expectedOwnerId)` for a fresh snapshot. They are not form actions. The app has no `useActionState` and no form library. Each action reads the user with `getUserId` from `@/features/auth/server` and answers with a typed result instead of throwing: `signed-out`, `other-account` when the user differs from `expectedOwnerId`, `rejected` when the zod schemas in `src/features/marks/schemas.ts` refuse the input, and `unavailable` when the database fails. They read and write through `src/features/marks/services/marks.ts`. `src/proxy.ts` lets a request with a `Next-Action` header past the route gate, so an expired session gets `signed-out` from the action instead of a redirect.
- `SessionLayer` renders `MarksSession` from `@/features/marks/server`, which passes the user id and the unawaited `loadMarks` promise to `StartMarksSession`. That promise may reject. Its effect starts the session for that owner, then turns the promise into a snapshot with `snapshotFromMarks`, a failed one when it rejects, and hands it to the store. `readMarks` uses `loadMarksSnapshot`, which logs a failed read. Signing out calls `endMarksSession` from `@/features/marks` first, which ends the session and clears the cache. When the owner changes from one account to `null` or to another account, `resetGlobeOnAccountChange` in `mount-globe.ts` clears the selected country and the next globe starts from the default camera. The first sign-in changes neither.
- The globe is imperative. `MapCanvas` imports `mapbox-gl` on the client, and `src/features/globe/mount-globe.ts` creates the map. `map-spin.ts`, `map-country-events.ts` and `map-store-sync.ts` beside it bind spin, country events and store sync. React never renders map content. The reconciliation sweep in `map-country-events.ts` waits for `sourcedata`, not `idle`, because `idle` never fires while the globe spins. The `/` page renders `MapCanvas`, so `/list` and `/stats` never load `mapbox-gl`. Leaving `/` calls `unmount` from `startGlobe`, which unbinds `style.load`, stops the spin, ends the store subscriptions and removes the map. `unmount` returns the camera and whether the globe still spins, and the next globe starts from that camera and spins only if the last one did. A search's pending fly stays in the selected-country store, so the next globe flies to it once its style loads.
- The country dataset is `src/features/countries/countries.generated.ts`, written by `bun run gen:countries` from the `world-countries` package. Never edit it by hand. Each entry has a `kind`, a `center` for fly-to and a `hasGlobeLabel` flag. The globe colours countries by the `iso_3166_1_alpha_3` code in the Mapbox `country-boundaries-v1` tileset, and a few of those codes are not ISO codes. Kosovo has no ISO code, so the tileset calls it `XKS` and `world-countries` calls it `UNK`. `src/features/globe/tileset-feature.ts` maps tileset codes to dataset codes for clicks, fills and the selected outline, so marks keep the dataset code. Add any other tileset code that differs from its dataset code to that map.
- `next.config.ts` turns on Cache Components and Partial Prefetching. Read request data, such as the session or marks, inside a `<Suspense>` boundary, as `src/app/(app)/layout.tsx` does for `SessionLayer`. Read the matching guide in `node_modules/next/dist/docs/` before you change caching or prefetching.
- Server-only code is every feature's `server.ts` (`@/features/<name>/server`), `src/shared/server/` (the Turso client and the env parser), `@/features/marks/services/marks`, `@/features/marks/apply-mark-change` and `@/features/marks/schemas`. Each one starts with `import "server-only"`, so importing it from client code fails the build.

`bun run build` and `bun run dev` need `TURSO_DATABASE_URL`, plus `TURSO_AUTH_TOKEN` unless the URL starts with `file:`. `src/shared/server/env.ts` parses them once and throws an error that names any missing one. To build without a database, use the CI values `TURSO_DATABASE_URL=libsql://ci-placeholder.turso.io` and `TURSO_AUTH_TOKEN=ci`. `bun run dev` also needs the Clerk values in README.md. Without a Mapbox token the globe shows a flat placeholder. Run `bun run setup` to write them to `.env.local`. It pulls the Clerk development keys and the Mapbox token, points `TURSO_DATABASE_URL` at `file:.data/dev.db` in this worktree, migrates it and creates the dev test user `agent+clerk_test@example.com`. It refuses a remote database URL, a database file outside this worktree's `.data/`, `pk_live_` or `sk_live_` keys and a Mapbox token that does not start with `pk.`. For a signed-in session, run `bun run sign-in-token`, open `/sign-in`, and after `window.Clerk.loaded` run `const signIn = await window.Clerk.client.signIn.create({ strategy: "ticket", ticket }); await window.Clerk.setActive({ session: signIn.createdSessionId });` with the printed token as `ticket`. `bun run check` sets its own build values, including a fixed `NEXT_SERVER_ACTIONS_ENCRYPTION_KEY`, a fake `pk_live_` Clerk key and a fake Mapbox token, so its bundle bytes match CI's unless `.env.local` sets other `NEXT_PUBLIC_` values.

Measure performance with `bun run perf -- --baseline <ref>`, never by hand and never with Lighthouse. It refuses a dirty tree, a `bun.lock` that differs from the baseline, a bun other than the `devEngines` pin (run `bunx bun@1.4.3 run perf` when your bun differs), and a database outside `.data/`. It seeds 49 marks for the dev test user in the local database, exports both commits under `.data/perf/trees/` through a temporary git index and builds them, serves each on its own port and kills each server by its PID. Chrome loads `/`, `/list` and `/stats` signed in, as a first visit and a repeat visit, alternating sides, under CDP throttling (150 ms RTT, 1.6 Mbps, 4x CPU) with Clerk Protect blocked. On `/` it also loads `/list` twice, once warm and once after clearing the cache and storage, clicks the tab bar link back to `/` and times the first globe frame and the seeded marks from the click. The cold return includes the `mapbox-gl` download after the click. The report gives each metric's median and median absolute deviation (MAD). A timing counts as faster or slower only when an exact two-sided Mann-Whitney test gives p < 0.01, which at 5 runs a side means the samples do not overlap, and the median moves by at least 50 ms or 5%, whichever is larger. A byte delta counts above 1 KB or 1%. It refuses fewer than 5 runs and a second run anywhere on the machine, through `~/.local/state/traviz/perf.lock`, because concurrent runs skew each other. Web Worker requests, such as Mapbox tiles, are not throttled. A baseline branch with an upstream is fetched first. When the local branch is behind, the harness measures the upstream commit and prints its SHA, and when the local branch has commits the upstream lacks, it refuses.

## Rules

Some older code still breaks these rules. Do not copy it. The table at the end says which rules a tool checks today.

- Use bun for every package and script command. Never use npm, pnpm or yarn.
- Import with the `@/` alias, never `../` or `./`. CSS imports and packages are the exception. `@/paths` resolves to `paths.ts` at the repo root, and `@/*` resolves to `src/*`.
- Import a feature from outside it only through `@/features/<name>` (its `index.ts`, safe on the client), `@/features/<name>/server` (its `server.ts`) or an action at `@/features/<name>/actions/<verb>`. Inside a feature, import a sibling as `@/features/<name>/<file>`. Every file under `src` sits in `app`, `features/<name>` or `shared`, or is `proxy.ts`. `src/shared` imports no feature.
- Never import a module only for its side effects, with a bare `import` or an `import {} from` that binds no name. `package.json` sets `"sideEffects": ["*.css"]`, so the bundler drops a local one, and a dropped `server.ts` import also skips its `server-only` guard. A bare import of CSS, `server-only` or `client-only` is fine.
- Build every route path with a function from `paths.ts`, such as `export const listPath = (): Route => "/list";`. Never write a route string inline. `typedRoutes` is on, so a static path function returns `Route` from `next` and its literal is checked against the app's routes. A path function that builds its result at runtime, such as `decoratedPath` for Clerk's `decorateUrl`, ends in `as Route`.
- Use `cn` from `@/shared/cn` for conditional class names.
- Never use a type assertion (`as`) outside `paths.ts`. Inside it, the only one allowed is `as Route` at the end of a path function that builds its result at runtime. Never use a non-null assertion (`!`) or `any`. `as const` is fine. Fix the type with narrowing, generics or `satisfies`. Parse an untyped value, such as a `JSON.parse` result, before you use it. Never use `@ts-ignore`, `@ts-expect-error` or `@ts-nocheck`.
- Type the parameter of a `.catch` handler as `unknown`, as in `.catch((error: unknown) => ...)`, and narrow it with `instanceof`. Never type it as `Partial<Error>` or `any`. A helper that takes the caught value names its parameter `cause: unknown`, the name `anti-slop/no-unknown-parameters` exempts.
- Make every data change through a Server Action. Each action lives in `src/features/<name>/actions`, with one verb per file and `"use server"` at the top. Never use a route handler or a client `fetch` for a mutation.
- Each action checks the user with `getUserId`, validates its input with zod, and only changes rows the user owns.
- Never put `"use server"` on a services or lib module. It turns every export into a public endpoint. Keep the modules that import `server-only` out of client code. Import `zod`, `@libsql/client` and `@clerk/nextjs/server` only from a module that starts with `import "server-only"`, a `"use server"` action or `src/proxy.ts`. An `import type` of them is fine anywhere.
- The marks actions must not call `revalidatePath` or `refresh`. That would rerender `MarksSession` and send a second snapshot that costs a round trip. The owner counts it as the session's first snapshot, so it is dropped once a fresh snapshot has landed.
- Put one React component in each file. Name the file after it in kebab-case (`src/features/country-list/country-row.tsx` exports `CountryRow`).
- Model each business operation once (single write path). Prefer one configurable component over near-copies, once a third copy appears.
- Change the country dataset only in `scripts/build-countries.ts`, then run `bun run gen:countries`. Never edit `countries.generated.ts` by hand.
- Write no comments. Use descriptive names instead of one-letter names, and use `T` for a single generic.
- Put tests next to the code they test, as `*.test.ts` or `*.test.tsx` under `src`, and run them with `bun run test`. `bun run test` only runs tests under `src`, so tests for `scripts` go in `src/shared/testing`. Tests can import modules that import `server-only`, because `bunfig.toml` preloads a stub for it. Run `bun run test:rules` after you change a rule in `tools/oxlint`. Bun's test runner cannot run those rule tests.
- Do not mock modules in tests. Pass dependencies in as arguments.
- Use Bun APIs, and imports from `bun` or `bun:*`, only in tests, `src/shared/testing` and `scripts`. The app runs on Node in production.
- A file listed in `files` in `tsconfig.pure.json` must not touch the DOM, Bun or Node, and everything it imports must be pure too. `bun run typecheck` compiles those files with only the ES2023 lib. To make a file pure, add it to `files` in `tsconfig.pure.json` and in that file's copy in `gates.json`.
- Keep each route's gzipped first-load JS and lazy JS within its entry in `bundle-budget.json`, plus 1% or 1 KB, whichever is larger. Lazy JS is every chunk that the first-load chunks reference as `static/chunks/<name>.js`, followed transitively, such as the `mapbox-gl` chunk that `import()` fetches after hydration. When a change needs more, run `bun run check`, then `bun run check:bundle --write`, copy the new `bundle-budget.json` into `bundleBudget` in `gates.json`, and commit both, so the growth shows in the diff. A budget that only went down needs no change to `gates.json`. Never preload JS in a route's HTML that the route does not load at first, such as the lazy `mapbox-gl` chunk. The check reads only the prerendered static shell, so it cannot see a preload inside a `<Suspense>` boundary that renders at request time.
- After a UI change, open every affected page and screenshot it at 375, 768 and 1440 px, with `bun run verify:shots` or in the dev server. Read `.claude/skills/verify-traviz/SKILL.md` first. It covers how to launch, sign in, drive and clean up. Fix layout breakage, overlap, clipped text and low contrast, then screenshot again. If you cannot run the dev server, say so instead of skipping this.
- Never loosen a check: no `continue-on-error`, no lint rule at `warn`, no higher `maxCrap`, no weaker react-doctor `blocking`, no inline `oxlint-disable` or `eslint-disable`. A lint rule may be off only in a file-scoped override listed in `lint-exemptions.json`, with the reason and when to remove it. A new entry needs a reviewer's sign-off. `gates.json` holds a copy of the CI workflow, `tsconfig.json`, `.oxlintrc.json`, `.fallowrc.json`, `doctor.config.json`, `.oxfmtrc.json`, `bunfig.toml`, the gate scripts, `devEngines` and the bundle budget, and `bun run check:gates` fails when they differ, or for the bundle budget when a number goes up, so a change that tightens a gate also updates `gates.json`.
- Before you report a task as done, run `bun run format`, then `bun run check`, and fix what they report.
