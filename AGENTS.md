# traviz

traviz is one Astro 7 app for marking countries on a globe as visited, want to go, or not interested. It renders every page on the server and ships hand-written TypeScript to the browser, with no client framework. Each Clerk user's marks are stored in a Turso (libSQL) database. Read this file before you change anything. `CLAUDE.md` is a symlink to it.

## How the app works

- `astro.config.ts` sets `srcDir` to `src` and `output: "server"`. The adapter is `@astrojs/vercel`, which production uses. `TRAVIZ_ADAPTER=node` selects `@astrojs/node` in standalone mode, which `bun run build:node`, `bun run start`, the bundle check, the verify scripts and the perf harness use. `scripts/serve-node.ts` runs that build: it answers a request for a static file with a gzipped copy it made at startup, as a CDN would, and hands every other request to the adapter's handler. Every stylesheet is inlined into the HTML (`inlineStylesheets: "always"`), so no page waits for a CSS request. Two Vite plugins live in that file. `serverOnlyGuard` makes `import "server-only"` an empty module on the server and a build error in client code. `inlineScripts` bundles each entry in its `INLINE_SCRIPT_ENTRIES` into one chunk, which a template imports as text from `virtual:traviz-inline-script/<name>` and inlines as a module script, and fails the build when a chunk contains an `import()`, because an inlined script has no file to import from. The entries are `src/features/app-shell/app-entry.ts`, which `app-layout.astro` inlines, and `sign-in-entry.ts`, `verify-entry.ts` and `account-menu-entry.ts` in `src/features/auth`.
- Routes: `/` (globe), `/list`, `/stats`, `/welcome` (the public landing page), `/sign-in`, `/sign-in/verify` and `/404`, the fragments `/fragments/globe`, `/fragments/list`, `/fragments/stats` and `/fragments/account-menu`, and the API routes `/api/marks/apply` and `/api/marks/read`. `src/pages` holds one thin file for each. `src/middleware.ts` gates each request through `gateRequest` in `src/shared/route-gate.ts`, which reads the route's row in `ROUTES` in `paths.ts`. `signedIn` routes send signed-out users to `/sign-in`, except `/`, which sends them to `/welcome`. `signedOut` routes send signed-in users to `/`, and `anyone` routes let both through. The match is exact, and a path with no row is treated as `signedIn`. The API routes are `anyone`, so an expired session gets `signed-out` from the handler instead of a redirect. The middleware puts the user on `Astro.locals.userId`, sets `cache-control: private, no-store` on a response that names no cache policy, so no browser or proxy keeps a signed-in page, and gzips the rendered response on the Node adapter, where no CDN does it. It does not run for the two prerendered pages, `/welcome` and `/fragments/account-menu`, which hold no user data.
- A new route needs a page under `src/pages`, a function in `paths.ts`, a row in `ROUTES`, an entry in the routes list above, and an entry in `NAVIGATION_ITEMS` in `src/features/app-shell/navigation.ts` if it is a tab. `src/shared/paths.test.ts` fails when a page or endpoint under `src/pages` has no row in `ROUTES`, on any dynamic or rest route, which exact matching cannot gate, and when a file under `src` other than a test spells a route's path inline.
- The server authenticates each request once. `authenticateRequest` in `@/features/auth/server` reads the session with `@clerk/backend` (`readClerkSession` in `src/features/auth/clerk-session-reader.ts`) and answers Clerk's `handshake` state with its redirect and headers. The reader sits behind the `SessionReader` type in `src/features/auth/authenticate.ts`, so tests pass a fake. `CLERK_AUTHORIZED_PARTIES` is optional: a comma-separated list of origins, such as `https://traviz.example`, that `parseAuthorizedParties` hands to Clerk, which then refuses a session token made for any other origin. Unset, the token's origin is not checked. `TRAVIZ_FIXED_USER_ID` signs every request in as that user without Clerk, for local runs. `src/shared/server/env.ts` refuses it, and `TRAVIZ_DB_DELAY_MS`, unless `TURSO_DATABASE_URL` starts with `file:`, so neither can be on in production.
- Sign-in uses Clerk email links only. There are no passwords and no social providers. The pages are `src/pages/sign-in/index.astro` and `src/pages/sign-in/verify.astro`, which render `sign-in-document.astro` and `verify-document.astro` inside `src/features/auth/sign-in/auth-layout.astro`. The form is custom code, with no Clerk UI bundle: `sign-in-page.ts` binds `src/features/auth/sign-in/email-link-form.astro` to `createEmailLinkSignIn` in `email-link-sign-in.ts`, and `verify-page.ts` binds `src/features/auth/sign-in/email-link-verification.astro` to `verifyEmailLink` in `email-link-verification.ts`. Both pages use their own stylesheet, `src/features/auth/sign-in.css`, and not `app.css`. Their scripts are inlined, so they call `clerkSession.loadNow()` as soon as the page is parsed, with no request before clerk-js. A sign-in page that becomes visible after another tab signed in goes to `/`.
- On the app pages `keepClerkSession` in `src/features/auth/keep-clerk-session.ts` calls `loadAfterPage` on `clerkSession` from `src/features/auth/clerk-session.ts`. It adds clerk-js after the window `load` event, once the browser is idle, then calls `window.Clerk.load()` once. A script that has not loaded after 15 s loses its tag, and a failed attempt is tried again after 1 s, then 4 s. Every attempt after the first adds `?attempt=<n>` to the URL, because Chrome hands a new tag for the same URL the stalled request. When all three fail, the failure is logged, and the next `online` event or return to the tab tries again. Every caller shares one load in flight. clerk-js keeps the short-lived `__session` cookie fresh, which the server reads. `keepClerkSession` sets `window.__internal_onAfterSetActive` to a function that ends the marks session and reloads the page. When the tab becomes visible, or comes back from the back-forward cache, `hasSessionChanged` in `session-cookies.ts` reads Clerk's cookies, and the tab reloads the same way when no client is active or the `__session` cookie belongs to another user. So a sign-out or an account change in another tab sends this tab to `/sign-in` or to the new account's marks. `keepClerkSession` does nothing when the build has no `PUBLIC_CLERK_PUBLISHABLE_KEY`.
- `account-button.astro` renders the account button, which shows the account's initial once clerk-js knows the email. The top bar shows the button at 768 px and up. Below that the globe view and the stats view render their own, and `/list` has none. `startAccountButton` in `start-account-button.ts` fetches `/fragments/account-menu` on the first hover, focus or click, appends it to `<body>` once and opens its `<dialog>` as a modal. The fragment is `account-menu.astro`: the dialog in `src/features/auth/account-menu/account-menu-dialog.astro`, its own CSS from `account-menu.css`, which `scopeUtilities` keeps from restyling the page, and the inlined `account-menu-entry.ts`. That script is a module graph of its own, so `startAccountMenu` in `account-menu.ts` takes the Clerk session and the marks store from `window.travizAccountMenu`, which `startAccountButton` sets. The menu holds the email and the sign-out (`account-section.ts`), a line for a snapshot that failed to load, the theme choice (`theme-picker.astro` and `mountThemePicker` in the theme feature) and the reset of all marks (`danger-zone.astro` and `mountDangerZone` in the marks feature). Signing out calls `endSession` on the marks store once Clerk's `signOut` resolves. When clerk-js cannot load, or `signOut` rejects, the session stays and the menu shows an alert. Once clerk-js has loaded, its `signOut` does not reject when the request to Clerk fails: it still navigates to `/sign-in`, where the server finds the session alive and sends the tab back to `/`, so that failure shows no alert.
- `/welcome` is prerendered (`export const prerender = true` in `src/pages/welcome.astro`), so the gate does not run for it. An inline script there, built by `signedInHintScript` in `src/features/auth/signed-in-hint.ts`, sends a visitor to `/` when this app's own Clerk client cookie says they are signed in. That cookie is `__client_uat_<suffix>`, with the suffix Clerk derives from the publishable key, because `__client_uat` cookies sit on the parent domain and another Clerk app there sets its own. The cookie is only a hint, so the gate has the last word: when it sends a signed-out request for `/` to `/welcome`, it sets the short-lived `traviz-signed-out` cookie from `src/shared/signed-out-cookie.ts`, and the script does not send the visitor back while that cookie is there. Without it, a hint the server disagrees with would bounce between the two pages forever.
- The signed-in pages share one document. `src/features/app-shell/app-layout.astro` renders the top bar, the tab bar, the globe slot and the scroll panel, the page's own view, the marks snapshot and the inlined app script. `startApp` in `src/features/app-shell/start-app.ts` starts the marks session, replays the early taps, starts the view router and the account button, and keeps the Clerk session. `startViewRouter` in `src/features/app-shell/view-router.ts` mounts each view once, when its DOM enters the document, through the `MountedView` contract in `src/shared/view.ts`: `showView` when its tab becomes active and `hideView` when it leaves. A view that is not active stays mounted and takes the `view-inactive` class (`content-visibility: hidden`). A tap on a nav link switches on `pointerdown` with `pushState`, and `popstate` switches back. A view that is not in the document yet is fetched from its `/fragments/<view>` route, which renders the same view component as the page, and the other views are prefetched one after another when the browser is idle after `load`. When a fragment cannot load, the link navigates as a normal link. The router sets `innerHTML`, so a `<script>` inside a fragment never runs. Every URL still renders its own view on a direct load. Beside the router, `reloadWhenStale` in `src/features/app-shell/resume-reload.ts` reloads the installed app (`display-mode: standalone`) when it becomes visible after 5 minutes or more hidden, because an iPhone can bring it back unresponsive and with an expired session. It keeps the page when the device is offline, since there is no service worker to serve a reload, and it never runs in a browser tab.
- Each page starts the marks read without waiting for it (`loadUserMarks` in `@/features/marks/server`) and passes the promise down, so the head, the inline CSS, the navigation and the headings leave the server before the database answers, and the marks-dependent part follows in the same response. `marks-snapshot.astro` embeds the snapshot as `<script type="text/plain" id="marks-snapshot">`. The wire format is form-encoded text, written and read by `src/features/marks/marks-wire.ts`, because the client code may not parse untyped JSON. `startMarksSession` reads the snapshot and starts the session for its owner. A failed read becomes a failed snapshot, and `loadMarksSnapshot` logs it.
- Marks are a `Marks` record from `src/features/marks/colors.ts`, keyed by country code. The pure reducer in `src/features/marks/marks-sync.ts` holds a base (empty or the server's marks), the pending changes and the problems, and the screen shows the pending changes applied over the base. `src/features/marks/marks-owner.ts` runs the reducer and sends one change at a time, in tap order, tagged with the owner it was made for. A change with no reply after 8 s rolls back with an `unavailable` problem. When its reply comes later and is ok, the change joins the base and the problem the deadline left is removed, leaving any newer problem. Either way the owner then reads a fresh snapshot. `src/features/marks/marks-store.ts` wraps the owner in `marksStore`, a store from `createStore` in `src/shared/store.ts` (`getState`, `setState`, and `subscribe` with the previous state), which exposes `marks`, `ownerId`, `saving`, `problems` and the actions. A failed change undoes its colour and leaves a problem on its country, and `markStatusText` in `src/features/marks/mark-status.ts` gives the text a view shows for it. The globe's selection store and the landing store use the same `createStore`. No view reads another view's DOM. Each one renders from the store it is given.
- `EARLY_TAPS_SCRIPT` from `src/features/marks/early-taps.ts` is an inline script in the head. It handles a tap on a state button from the first paint, before the app script runs: it flips `aria-pressed` and records the tap, and `replayEarlyTaps` sends the recorded taps through the store once it exists.
- Data changes go through the API routes, one verb per file: `src/pages/api/marks/apply.ts` for set, clear and reset, and `src/pages/api/marks/read.ts` for a fresh snapshot. Each exports only `POST` and calls `handleMarkChange` or `handleMarksRead` from `@/features/marks/server`. The handlers in `src/features/marks/marks-api.ts` refuse a request whose `Origin` is not the site's with 403, read the user from `locals`, validate the input with the zod schemas in `src/features/marks/schemas.ts`, and answer with a typed result instead of throwing: `signed-out`, `other-account` when the user differs from the expected owner, `rejected` when the schemas refuse the input, and `unavailable` when the database fails. They read and write through `src/features/marks/services/marks.ts`. The client calls them with `fetch` through `src/features/marks/marks-transport.ts`.
- `/list` is `src/features/country-list`. The server renders the first 12 rows and, in each section, a spacer as tall as the rows that are missing, and ships every row as a text block in the page. `list-view.ts` builds the other rows from a `<template>` after the first paint, 40 at a time, so the first frame stays small and nothing shifts. A search, a status filter or a continent change moves the row nodes that exist and never renders them again. `list-model.ts` holds the pure logic.
- `/stats` is `src/features/stats`. `stats-summary.astro` renders the totals and one card per continent, and `stats-view.ts` updates them from the marks store with the model in `stats-model.ts`, which the server uses for the first render too.
- The theme is `system`, `light` or `dark`, in `src/features/theme`. Every colour token in `src/shared/styles/theme.css` is a `light-dark()` pair. `src/features/app-shell/app.css`, `src/features/landing/landing.css`, `src/features/auth/sign-in.css` and `src/features/auth/account-menu.css` all import Tailwind and that file, so every page reads one set of tokens. `color-scheme` on `:root` picks the side of each pair: `light dark` by default, or the `data-theme` attribute on `<html>` when the user chose one. `chooseTheme` in `theme-store.ts` sets that attribute and saves the choice in localStorage under `traviz-theme`, and `THEME_SCRIPT`, inline in every page's head, sets it again before the first paint and again on a `storage` event, which is how a choice made in another tab arrives. `subscribeTheme` notifies through a `MutationObserver` on that attribute and the `prefers-color-scheme` media query, and not from `chooseTheme`, because the account menu and the globe engine each bundle their own copy of the module, and the attribute is the one thing the copies share. The canvas cannot read the tokens, so `globe-palette.ts` holds the globe's colours for both themes, and `createGlobe` redraws with the other palette when `subscribeTheme` fires. `STATE_COLORS` in `colors.ts` are `var()` references for DOM styles only. Use `text-white` on a fill that stays the same in both themes (`bg-ink-deep`, `bg-want`, `bg-negative`), `bg-active text-on-active` for the selected nav item, and `text-negative-text` for error text. `bg-ink` and `text-canvas` swap with the theme.
- The fonts are Instrument Sans, from `@fontsource-variable/instrument-sans`, and Geist Mono for the `font-mono` text: counts, percentages, country codes and the small uppercase labels. `src/shared/styles/fonts.css` imports `src/shared/styles/geist-mono.generated.css`, the one `@font-face` rule for `src/shared/styles/geist-mono-subset.woff2`. `bun run gen:fonts` writes both from the latin file of `@fontsource-variable/geist-mono`, with `subset-font`: the subset holds printable ASCII and the middle dot (`U+0020-007E`, `U+00B7`) and the weights 400 to 700, about 10 KB where the package's latin file is 23 KB. The rule's `unicode-range` names the same characters, so any other character renders in the next font of `--font-mono` and the browser never asks this file for it. To put another character in mono text, add its range to `CODE_POINT_RANGES` in `scripts/build-fonts.ts` and run `bun run gen:fonts`.
- Icons are Radix SVGs copied into `src/shared/icons`, drawn in one of two ways. The names in `ICON_NAMES` in `icons.ts` are CSS masks: `icons.css` has one `icon-<name>` utility for each, and `icon.astro` renders one. `app.css` imports `icons.css`, so they work on the app pages and in the account menu, which opens over them. The names in `INLINE_ICON_NAMES` are inline SVG, which `inline-icon.astro` renders from the file, for the sign-in pages and the account menu's own content, whose stylesheets do not carry the masks. To add an icon, copy its 15 px SVG from Radix Icons and add its name to one list, with the utility when it is a mask. `icons.test.ts` fails when the files, the names and the utilities disagree. Never install an icon package.
- The landing page's hero lists the 195 sovereign countries as buttons that cycle a local mark through the three states. `src/features/landing/landing-entry.ts` calls `startLanding`, which reads the countries from the rendered buttons, keeps the marks in a store from `createLandingStore` in `landing-store.ts`, and updates the DOM in `render-landing.ts`. The marks start from a labeled sample in `landing-marks.ts` and are never saved. The templates render that sample with the helpers in `landing-view.ts` and the class names in `landing-classes.ts`, which the client code uses too, so the first paint and a later update produce the same markup. `loadPreviewGlobe` from `@/features/globe/core` draws the marks on a non-interactive globe (`createGlobe` with `isInteractive: false`) that spins and flies to each pick. The engine, the outlines and the country dataset load as lazy chunks. The page preloads Instrument Sans, which the app pages do not, and links to `/sign-in` with plain anchors. `src/pages/404.astro` shares the landing page's styles and ships no module script. `DESIGN.md` at the repo root holds the landing page's concept and system.
- The globe is imperative and draws on a Canvas 2D context. `src/features/globe/globe-view.astro` renders the view: the canvas host, the search, the country card, the sheet, the hint, the legend, the zoom buttons and the progress card. `mountGlobeView` in `globe-view.ts` mounts it and owns the selection store from `createSelectionStore` in `selected-country.ts`. The engine is lazy JS in a module graph of its own. `globe-engine-entry.ts` calls `registerGlobeEngine` in `globe-engine.ts`, which puts the engine on `window.travizGlobeEngine` (`globe-engine-contract.ts`) and brings `create-globe.ts`, with `d3-geo`, and the outlines in `country-topology.generated.ts`. `lazy-script.astro` renders that entry as an `async` module script on `/`, and anywhere else as a `<template>` that holds the script's URL, which `activateLazyScript` in `lazy-script.ts` turns into a script the first time the globe view shows. So `/list` and `/stats` do not load the engine until the user opens the Globe tab, and the globe fragment, whose scripts never run, can still load it. When the view mounts there, `preloadLazyScript` adds a `modulepreload` for the entry file alone, about 1 KB, so the tab switch fetches the engine's chunks in one round trip and not two. Chrome fetches only that file for it. A browser that also fetches a preloaded module's imports gets the whole engine early. The entry must stay a file of its own for that, which it does because it shares its chunks with the landing page, and `bun run check:bundle` fails when it is not. The view hands the marks store and the selection store to the engine's `start`, because the engine's graph has its own copy of every module, which creates the globe after the next paint. `startGlobe` in `mount-globe.ts` binds the spin (`map-spin.ts`) and the store sync (`map-store-sync.ts`). Hiding the view pauses both, and showing it resumes them with the same camera. `globe-scene.ts` projects with a vertical perspective at the scale `globeScale` in `globe-camera.ts` gives, which is Mapbox's globe scale matched at 45° of latitude, viewed from 1.5 viewport heights, so a zoom level shows what the Mapbox globe showed. A country part wholly in front of the horizon goes through the tracer in `globe-scene.ts`, and a part that crosses the horizon goes through `d3-geo`'s clipped projection stream. `buildScene` gives each part a bounding cap, the normalized mean of its outer ring's points and the largest angle from it to one of them, which decides whether the part is hidden, in front or on the horizon, and which `countryAt` checks before `geoContains`. The tracer never calls `closePath`, which costs Chrome about 5 µs per ring, and `fill` closes each ring anyway. The globe redraws only when the camera, the marks, the selection, the size, the device pixel ratio, the theme or a loaded web font change. The canvas is a focusable `region` named Globe: the arrow keys pan and `+`, `=` and `-` zoom (`globe-keys.ts`). A country with no outline, or whose outline is under 8 px on screen, gets a dot at its dataset centre (`globe-markers.ts`). A tap on a dot picks it, the selected dot first, and a tap within 12 px of a dot picks it unless the tap is on another country nearer that country's centre. At 768 px and up a picked country shows in `country-card.astro`, in the panel on the right. Below that it opens the sheet (`country-sheet.astro` and `country-sheet.ts`), which the view moves to `<body>` so its full-screen backdrop sits above the tab bar, and which a drag down dismisses (`sheet-drag.ts`). Closing it plays a 200 ms exit animation, and `afterExit` in `sheet-exit.ts` clears the selection when the animation finishes or is cancelled, or after 400 ms when it does neither, so a backdrop that iOS never finishes animating cannot stay and swallow every tap. The country search (`country-search.astro`, `country-search.ts` and the pure `country-search-state.ts`) is rendered twice: one stays in the view for narrow screens, and the view moves the other into the top bar's `data-top-bar-globe-tools` slot, which shows on the globe view only. A search's pending fly stays in the selection store, so an engine that starts later flies to it. When the marks owner changes from one account to `null` or to another account, `startGlobe` clears the selection, moves the globe back to the default camera and lets it spin again. The first sign-in changes neither.
- The country dataset is `src/features/countries/countries.generated.ts`, written by `bun run gen:countries` from the `world-countries` package. Each entry has a `kind`, a `center` for fly-to and a `hasGlobeLabel` flag. The same script writes the globe outlines in `src/features/globe/country-topology.generated.ts` from the Natural Earth 50m topology in `world-atlas`. It keys each outline by the dataset code through `ccn3`, names the codes of the outlines with no ISO number (Kosovo is `UNK`, Somaliland joins `SOM`, Northern Cyprus joins `CYP`), and splits the overseas parts of France, the Netherlands and Norway off to their own codes. Siachen Glacier stays as land with no code. It then keeps the top 15% of points by planar weight, quantizes to 1e4 and packs the result with `packTopology` in `src/features/globe/topology-codec.ts`: the country codes, the arc indexes of each ring and the delta-coded arc points become three strings of printable ASCII, where a small number takes one character. The script fails when `unpackTopology` does not give back the quantized rings. `buildScene` unpacks them when the engine starts, so the browser ships no `topojson-client`, and the outlines gzip to about 36 KB instead of the 50 KB the topology took as an object literal. Planar weights use no trigonometry, so the output is the same on every platform. Never edit either file by hand.
- Server-only code is every feature's `server.ts` (`@/features/<name>/server`), `src/shared/server/` (the Turso client, the env parser and the gzip helper), `@/features/auth/authenticate`, `@/features/auth/clerk-session-reader`, `@/features/marks/services/marks`, `@/features/marks/apply-mark-change`, `@/features/marks/marks-api` and `@/features/marks/schemas`. Each one starts with `import "server-only"`, so importing it from client code fails the build.
- On Vercel, `@astrojs/vercel` builds one Node function that renders every server route and streams its response, and writes `/welcome`, `public/` and the hashed files under `/_astro` as static files, which Vercel serves before the function without running the middleware. The function's Node version is the one the build runs on, which `engines.node` in `package.json` keeps at 24. `vercel.json` names the framework, the install command and the build command. The middleware runs inside the function, not at the edge, because the only static page, `/welcome`, needs no gate.

| ------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `bun run dev`                   | Astro dev server on port 4321. Needs the `.env.local` values that `bun run setup` writes                                                                                 |
| `bun run build`                 | Production build with the Vercel adapter, into `.vercel/output`                                                                                                          |
| `bun run build:node`            | The same build with the Node adapter, into `dist`                                                                                                                        |
| `bun run start`                 | Serve the Node build with `scripts/serve-node.ts`, on `HOST` and `PORT` from the environment, by default `localhost:4321`                                                |
| `bun run format`                | Format with oxfmt                                                                                                                                                        |
| `bun run lint`                  | `astro sync`, so Astro's generated types exist, then oxlint with type-aware rules and the local `anti-slop` and `boundaries` plugins. It checks `.astro` frontmatter too |

| `bun run check:docs`            | Fail when AGENTS.md, README.md or `docs/` names a missing path or script                                                                                                 |
| `bun run test`                  | bun tests under `src`                                                                                                                                                    |
| `bun run test:rules`            | Lint rule tests in `tools/oxlint`, run with Node 24                                                                                                                      |

| `bun run fallow`                | `astro sync`, then the dead code, duplication and complexity report                                                                                                      |

`bun run build`, `bun run dev` and `bun run start` need `TURSO_DATABASE_URL`, plus `TURSO_AUTH_TOKEN` unless the URL starts with `file:`. `src/shared/server/env.ts` parses them once and throws an error that names any missing one. To build without a database, use the CI values `TURSO_DATABASE_URL=libsql://ci-placeholder.turso.io` and `TURSO_AUTH_TOKEN=ci`. The server also needs `CLERK_SECRET_KEY` and `PUBLIC_CLERK_PUBLISHABLE_KEY`, or `TRAVIZ_FIXED_USER_ID` with a `file:` database, and takes the optional `CLERK_AUTHORIZED_PARTIES`. `PUBLIC_CLERK_PUBLISHABLE_KEY` is also read at build time, for the client code. Both the build and the server fall back to `NEXT_PUBLIC_CLERK_PUBLISHABLE_KEY`, the name the Next app used, when the new name is not set, so a host that still has the old variable keeps working. Run `bun run setup` to write the development values to `.env.local`. It takes the Clerk development keys from `.env.local` when they are there, and from the `clerk` CLI otherwise. It finds or creates the dev test user with the CLI, or with Clerk's Backend API when the CLI is not installed, as `bun run sign-in-token` does. It points `TURSO_DATABASE_URL` at `file:.data/dev.db` in this worktree, migrates it and creates the dev test user `agent+clerk_test@example.com`. It refuses a remote database URL, a database file outside this worktree's `.data/`, and `pk_live_` or `sk_live_` keys. For a signed-in session, run `bun run sign-in-token`, open `/sign-in`, and after `window.Clerk.loaded` run `const signIn = await window.Clerk.client.signIn.create({ strategy: "ticket", ticket }); await window.Clerk.setActive({ session: signIn.createdSessionId });` with the printed token as `ticket`. `bun run check` sets its own build values, with a fake `pk_live_` Clerk key, so its bundle bytes match CI's.

`bun run check:bundle` reads the Node build in `dist`. It starts `scripts/serve-node.ts` twice on free local ports with a temporary empty database, once with `TRAVIZ_FIXED_USER_ID` for the `signedIn` routes and once with placeholder live Clerk keys and no cookie for the others, fetches every row of `ROUTES` that is not an API route, and stops both servers. It measures the HTML a visitor gets, not a build manifest, so a script or preload that only a server render adds is counted. For each route it budgets three gzipped sizes. First-load JS is the page's inline scripts, gzipped together, plus each script file it loads and what those import statically. An inline block that is not JavaScript, such as the marks snapshot, is not counted. Lazy JS is every other chunk under `/_astro` that the first-load code, a script that a `<template data-lazy-script>` in the HTML defers, or another lazy chunk names. So the globe engine and its outlines are first-load JS on `/`, which loads them at once, and lazy JS on `/fragments/globe`. HTML is the whole document, with its inline CSS and scripts. It also fails on a `<link rel="preload" as="script">` or `modulepreload` for a file outside the route's first load, on a route with no budget, on a budgeted route that was not rendered, when `/`, `/list`, `/stats`, `/welcome`, `/sign-in`, `/sign-in/verify` or `/fragments/account-menu` runs no module script, which is what a script dropped by `sideEffects` looks like, and when `/` or `/fragments/globe` names no lazy script file, which is what an engine that was inlined into the page looks like. `bun run check` passes `--production-static .vercel/output/static`, which fails when the Vercel build's JS or prerendered HTML differs from the measured Node build.

Measure performance with `bun run perf -- --baseline <ref>`, never by hand and never with Lighthouse. It refuses a dirty tree, a `bun.lock` that differs from the baseline (pass `--allow-lockfile-diff` when adding or removing a dependency is the change you measure; each side installs its own lockfile), a bun other than the `devEngines` pin (run `bunx bun@1.4.3 run perf` when your bun differs), and a database outside `.data/`. It seeds 49 marks in the local database, exports both commits under `.data/perf/trees/` through a temporary git index and builds them, serves each on its own port and kills each server by its PID. A commit from before the move to Astro, which has a Next config file at its root, is built with `next build` and served with `next start`. Any other commit is built with the Node adapter and served by this checkout's `scripts/serve-node.ts`, so both sides send gzipped static files. With Clerk development keys in `.env.local` it signs in with a sign-in token for the dev test user, and loads clerk-js on `/sign-in` itself when the page has not loaded it after 5 s. Without them it refuses, unless `--fixed-user` is passed and both commits are Astro commits: then both servers run with `TRAVIZ_FIXED_USER_ID`, the builds leave clerk-js out, and the report says so. Chrome loads `/`, `/list` and `/stats` signed in, and `/welcome` in a second browser that never signs in, as a first visit and a repeat visit, alternating sides, under CDP throttling (150 ms RTT, 1.6 Mbps, 4x CPU) with Clerk Protect blocked. `--route <path>`, which can repeat, measures only those routes. On `/` it also loads `/list` twice, once warm and once after clearing the cache and storage, clicks the tab bar link back to `/` and times the first globe frame and the seeded marks from the click. The seeded marks count as on screen only in rendered text (`innerText`), so text that is not shown yet does not count. The first globe frame is the first Canvas 2D `fill` or `stroke`, or WebGL draw, on a canvas in the document. The cold return includes the globe engine and outline downloads after the click. The report gives each metric's median and median absolute deviation (MAD), and the script bytes and all bytes each load transferred. A timing counts as faster or slower only when an exact two-sided Mann-Whitney test gives p < 0.01, which at 5 runs a side means the samples do not overlap, and the median moves by at least 50 ms or 5%, whichever is larger. A byte delta counts above 1 KB or 1%. It refuses fewer than 5 runs and a second run anywhere on the machine, through `~/.local/state/traviz/perf.lock`, because concurrent runs skew each other. Web Worker requests are not throttled. A baseline branch with an upstream is fetched first. When the local branch is behind, the harness measures the upstream commit and prints its SHA, and when the local branch has commits the upstream lacks, it refuses.

## Rules

Some older code still breaks these rules. Do not copy it. The table at the end says which rules a tool checks today.

- Use bun for every package and script command. Never use npm, pnpm or yarn.
- Import with the `@/` alias, never `../` or `./`. CSS imports and packages are the exception. `@/paths` resolves to `paths.ts` at the repo root, and `@/*` resolves to `src/*`.
- Import a feature from outside it only through `@/features/<name>` (its `index.ts`, safe on the client), `@/features/<name>/core` (its `core.ts`), `@/features/<name>/server` (its `server.ts`) or one of its `.astro` or `.css` files by path. A `core.ts` exports only code that needs no server module, and that imports other features only through their `core.ts`. The landing page's code and the globe engine import other features only through `core`, because an `index.ts` reaches the stores, which would put the app's code in the landing page's JS. Inside a feature, import a sibling as `@/features/<name>/<file>`. Every file under `src` sits in `pages`, `features/<name>` or `shared`, or is `middleware.ts` or `env.d.ts`. `src/shared` imports no feature.
- Write no client framework code. All browser behaviour is hand-written TypeScript: a view module takes its host element and the stores it needs as arguments, and keeps its pure logic in a separate module that `bun test` can run without a DOM.
- A `<script>` in an `.astro` file only loads an entry file, never code of its own: through `src`, such as `<script src="@/features/landing/landing-entry.ts">`, or inlined from `virtual:traviz-inline-script/<name>` once the entry is in `INLINE_SCRIPT_ENTRIES` in `astro.config.ts`. Inline an entry when its page needs it at once and it shares no chunk worth caching. Name the entry `<something>-entry.ts`, keep it to imports and one call, and list it in `"sideEffects"` in `package.json`. `fallow` cannot see imports inside a template's `<script>`, so it treats `src/features/*/*-entry.ts` as entry points. Use `is:inline` only for a script that must run before the first paint, and build its source from a tested function, as `EARLY_TAPS_SCRIPT` does.
- Never import a module only for its side effects, with a bare `import` or an `import {} from` that binds no name. `package.json` sets `"sideEffects"` to CSS files and the entry files, so the bundler drops any other local one. A bare import of CSS, `server-only` or `client-only` is fine.
- Build every route path with a function from `paths.ts`, such as `export const listPath = (): Route => "/list";`. Never write a route string inline. A path function that builds its result at runtime ends in `as Route`. None does today.
- Use `cn` from `@/shared/cn` for conditional class names in TypeScript, and `class:list` in a template.
- Never use a type assertion (`as`) outside `paths.ts`. Inside it, the only one allowed is `as Route` at the end of a path function that builds its result at runtime. Never use a non-null assertion (`!`) or `any`. `as const` is fine. Fix the type with narrowing, generics or `satisfies`. Parse an untyped value before you use it. On the server use zod. In client code, where zod must not load, write a decoder that returns typed values, as `marks-wire.ts` does. Never use `@ts-ignore`, `@ts-expect-error` or `@ts-nocheck`.
- Type the parameter of a `.catch` handler as `unknown`, as in `.catch((error: unknown) => ...)`, and narrow it with `instanceof`. Never type it as `Partial<Error>` or `any`. A helper that takes the caught value names its parameter `cause: unknown`, the name `anti-slop/no-unknown-parameters` exempts.
- Make every data change through an API route under `src/pages/api`, with one verb per file. The file exports only `POST` and only calls a `handle<Verb>` function from a feature's `server.ts`. Never change data from a page's frontmatter, from a `GET`, or from the middleware.
- Each handler refuses a request from another origin, takes the user from `locals`, validates its input with zod, and only changes rows the user owns.
- Keep the modules that import `server-only` out of client code. Import `zod`, `@libsql/client` and `@clerk/backend` only from a module that starts with `import "server-only"`. An `import type` of them is fine anywhere.
- A marks handler answers with its typed result only. It never redirects and never renders a page, because the client applies the result to the marks it already shows.
- Put one component in each `.astro` file. Name every file in kebab-case.
- Model each business operation once (single write path). Prefer one configurable component over near-copies, once a third copy appears.
- Change the country dataset and the globe outlines only in `scripts/build-countries.ts`, then run `bun run gen:countries`. Never edit `countries.generated.ts` or `country-topology.generated.ts` by hand.
- Change the Geist Mono subset only in `scripts/build-fonts.ts`, then run `bun run gen:fonts`. Never edit `geist-mono.generated.css` or replace `geist-mono-subset.woff2` by hand.
- Write no comments. Use descriptive names instead of one-letter names, and use `T` for a single generic.
- Put tests next to the code they test, as `*.test.ts` under `src`, and run them with `bun run test`. `bun run test` only runs tests under `src`, so tests for `scripts` go in `src/shared/testing`. Tests can import modules that import `server-only`, because `bunfig.toml` preloads a stub for it. Run `bun run test:rules` after you change a rule in `tools/oxlint`. Bun's test runner cannot run those rule tests.
- Do not mock modules in tests. Pass dependencies in as arguments.
- Use Bun APIs, and imports from `bun` or `bun:*`, only in tests, `src/shared/testing` and `scripts`. The app runs on Node in production.
- A file listed in `files` in `tsconfig.pure.json` must not touch the DOM, Bun or Node, and everything it imports must be pure too. `bun run typecheck` compiles those files with only the ES2023 lib. To make a file pure, add it to `files` in `tsconfig.pure.json` and in that file's copy in `gates.json`.
- Keep each route's gzipped first-load JS, lazy JS and HTML within its entry in `bundle-budget.json`, plus 1% or 1 KB, whichever is larger. When a change needs more, run `bun run check`, which builds both adapters, then `bun run check:bundle --write`, copy the new `bundle-budget.json` into `bundleBudget` in `gates.json`, and commit both, so the growth shows in the diff. `--write` refuses a build with a bundle problem, and a budget file from an older format must be deleted first. A budget that only went down needs no change to `gates.json`. Never preload JS in a route's HTML that the route does not load at first, such as the lazy globe chunks. Do not preload a web font on the app pages: it measured as a later first paint on a slow link.
- Keep CSS inline and JS non-blocking. Never add a `<link rel="stylesheet">` or a script without `type="module"`, `async` or `defer` to a page's head, other than the inline head scripts.
- After a UI change, open every affected page and screenshot it at 375, 768 and 1440 px, with `bun run verify:shots` or in the dev server. Read `.claude/skills/verify-traviz/SKILL.md` first. It covers how to launch, sign in, drive and clean up. Fix layout breakage, overlap, clipped text and low contrast, then screenshot again. If you cannot run the server, say so instead of skipping this.
- Never loosen a check: no `continue-on-error`, no lint rule at `warn`, no higher `maxCrap`, no weaker `astro check`, no inline `oxlint-disable` or `eslint-disable`. A lint rule may be off only in a file-scoped override listed in `lint-exemptions.json`, with the reason and when to remove it. A new entry needs a reviewer's sign-off. `gates.json` holds a copy of the CI workflow, `tsconfig.json`, `tsconfig.pure.json`, `.oxlintrc.json`, `.fallowrc.json`, `.oxfmtrc.json`, `bunfig.toml`, the gate scripts, `devEngines` and the bundle budget, and `bun run check:gates` fails when they differ, or for the bundle budget when a number goes up, so a change that tightens a gate also updates `gates.json`.
- Before you report a task as done, run `bun run format`, then `bun run check`, then `bun run fallow`, and fix what they report.
